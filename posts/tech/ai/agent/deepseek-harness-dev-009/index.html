概述

插件拿到的是与 Harness 同级的运行时能力：能注册工具、读文件、发请求。安全因此不是可选项，而是插件设计的默认组成。本篇分两部分：策略钩子（把权限与脱敏做成策略而不是焊死在工具里）和后台任务（长工作的正确生命周期）。对标社区 secret-guard、safety-net、PerryLink/dsh-defend 等安全插件的核心思路。

一、安全模型：策略与工具分离

社区安全插件的共识做法：权限和沙箱做成策略，不写进工具本体。框架在工具执行流水线上提供一排扩展点：

扩展点职责典型用途
pre-execute可扩展的允许/拒绝/询问策略命令白名单、路径保护
guard最终的单调拒绝，后续监听器无法撤销红线兜底（如禁止 rm -rf /）
execute 包装器给分发加截止时间、重试或指标采集超时治理
post-execute替换展示内容或返回值、拦截结果、附加模型可见上下文脱敏、结果改写
result只读观测归一化后的不可变结果审计日志

注意两个语义细节：

  • 内容替换不影响程序侧取值（PTC 程序拿到的还是原值）；
  • 保密策略要屏蔽或替换值本身，而不是只改展示。

1.1 精确接线：谁在哪一步、能不能翻案

dsh-tools 的调用流水线是固定顺序的，选错位置就等于写错语义：

tools/pre-execute  （waterfall，可重排）→ 允许/拒绝/询问
      ↓
已注册 guard       （ctx.tools.guard(fn)，同步、单调）→ 只能拒绝，后续监听器无法翻案
      ↓
tools/execute      （环绕包装）→ 超时/重试/指标；唯一可替换必填 signal 的视图
      ↓
tools/post-execute → 检查/替换内容或值、阻止、附加有序上下文
      ↓
finalizeContent    → 工具自己持有的内容收尾
      ↓
tools/result       （emit，只读）→ 观测冻结后的最终结果

三个直接影响写法的约束：

  • tools/pre-execute 不能改写 exec.arguments（有意设计，避免日志与实际运行内容脱节）。想改输入只能用 agent/pre-step 或参数层。
  • guard 是"单调"的：同步函数、只能收紧；返回理由即拒绝。红线兜底放这里，别放 pre-execute（那里可能被别的监听器放宽）。
  • 取消与失败都有结构化结果码：ABORTED_BEFORE_DISPATCH（主体前取消）、ABORTED（主体后取消）、TOOL_TIMEOUT（包装层超时）、UNKNOWN_TOOL（未知工具或工具抛错）。审计时记 result 里的这些码，比记自然语言可靠。

仍以 @deepseek-ai/dsh-tools 各版本 README 为最终依据；本篇把重点放在两个 100% 稳定的落点：基于 tools/result 事件的审计，以及工具化的敏感信息扫描。策略钩子给出设计范式与接线位置，具体签名接入时以当版 README 校准。

二、稳定落点一：审计日志（tools/result）

官方事件文档确认 tools/result 是 Cordis 事件，载荷为 (exec, result)。审计插件只用这一个事件就能覆盖全部工具调用：

 1// src/index.ts
 2import { appendFile, mkdir, readFile } from 'node:fs/promises'
 3import { homedir } from 'node:os'
 4import { dirname, join } from 'node:path'
 5import type { Context } from '@deepseek-ai/cordis'
 6import Schema from '@deepseek-ai/schemastery'
 7import { defineTool } from '@deepseek-ai/dsh-tools'
 8
 9export interface Config {
10  auditLog: string
11  redact: boolean
12  patterns: string[]
13}
14
15export const Config: Schema<Config> = Schema.object({
16  auditLog: Schema.string().default('~/.dsh/audit-lite/audit.jsonl').description('审计日志文件'),
17  redact: Schema.boolean().default(true).description('记录前脱敏'),
18  patterns: Schema.array(Schema.string()).default([
19    'sk-[A-Za-z0-9]{20,}',              // API Key 形态
20    'AKIA[0-9A-Z]{16}',                 // AWS AccessKey
21    '-----BEGIN [A-Z ]*PRIVATE KEY-----',// PEM 私钥
22  ]).description('脱敏正则列表'),
23})
24
25export const name = 'audit-lite'
26export const inject = ['tools']
27
28export function apply(ctx: Context, config: Config) {
29  const logFile = expandHome(config.auditLog)
30  const regexes = config.patterns.map((p) => new RegExp(p, 'g'))
31
32  // 日志目录可能不存在：启动时确保创建（失败不阻塞插件加载，appendFile 处再兜底）
33  void mkdir(dirname(logFile), { recursive: true }).catch(() => {})
34
35  function redact(text: string): string {
36    return regexes.reduce((acc, re) => acc.replace(re, '[REDACTED]'), text)
37  }
38
39  // 1) 审计：每次工具结果落一条 JSONL
40  ctx.on('tools/result', (exec, result) => {
41    const text = result.content
42      .map((b: any) => (b.type === 'text' ? b.text : `[${b.type}]`))
43      .join('')
44    const line = JSON.stringify({
45      ts: new Date().toISOString(),
46      tool: exec.name,
47      args: config.redact ? redact(JSON.stringify(exec.arguments)) : JSON.stringify(exec.arguments),
48      result: config.redact ? redact(text.slice(0, 2000)) : text.slice(0, 2000),
49    })
50    void appendFile(logFile, `${line}\n`).catch(() => {})
51  })
52
53  // 2) 工具化：让模型自己也能扫敏感信息
54  ctx.tools.register(
55    defineTool({
56      name: 'secret_scan',
57      description:
58        '扫描文本中的敏感信息（API Key、私钥、令牌等），返回命中位置与类型，不返回明文。'
59        + '适用：提交前自查、日志检查。',
60      parameters: {
61        path: { type: 'string', required: true, description: '要扫描的本地文件路径' },
62      },
63      output: {
64        schema: {
65          type: 'object',
66          properties: {
67            scanned: { type: 'string' },
68            findings: { type: 'array' },
69          },
70        },
71        render: (_args, value) => [
72          {
73            type: 'text',
74            text: value.findings.length
75              ? value.findings.map((f: any) => `第 ${f.line} 行命中「${f.kind}」`).join('\n')
76              : '未发现敏感信息。',
77          },
78        ],
79      },
80      async execute(args, exec) {
81        const text = await readFile(args.path, { encoding: 'utf8', signal: exec.signal })
82        const findings: { line: number; kind: string }[] = []
83        const kinds = ['api-key', 'aws-access-key', 'private-key']
84        text.split('\n').forEach((line, i) => {
85          config.patterns.forEach((p, pi) => {
86            if (new RegExp(p).test(line)) findings.push({ line: i + 1, kind: kinds[pi] ?? `pattern-${pi}` })
87          })
88        })
89        return { scanned: args.path, findings }
90      },
91    }),
92  )
93}
94
95function expandHome(p: string): string {
96  return p === '~' || p.startsWith('~/') ? join(homedir(), p.slice(2)) : p
97}

2.1 设计要点

  • 审计与工具解耦：审计走事件（观测一切调用），扫描走工具（模型主动用）；
  • 脱敏在记录侧：日志文件不落明文——审计日志本身就是高价值目标；
  • findings 不含明文：只报行号与类型，模型不需要看到密钥内容；
  • patterns 进 Config：不同团队有不同红线，yaml 可改。

三、稳定落点二：把「红线」做成可执行策略

上表的 pre-execute / guard 是执行前拦截；在签名未确认的版本，有一个等价的稳定模式——包装工具：注册一个「闸门工具」让模型先调，或直接用 execute 包装器思路。这里给出社区 safety-net（破坏性命令拦截）的范式代码骨架，接线处以当版参考为准：

 1// 范式：破坏性命令判定（纯函数，便于单测）
 2export interface Verdict { action: 'allow' | 'ask' | 'block'; reason?: string }
 3
 4const DESTRUCTIVE = [
 5  { re: /\brm\s+(-\w+\s+)*-\w*[rf]/, why: '递归/强制删除' },
 6  { re: /\bgit\s+push\s+.*--force/, why: '强制推送' },
 7  { re: /\bgit\s+reset\s+--hard/, why: '硬重置丢弃改动' },
 8  { re: /\bdd\s+if=/, why: '原始磁盘写入' },
 9  { re: />\s*\/dev\/sd[a-z]/, why: '直接写块设备' },
10]
11
12export function judge(command: string, allowlist: string[] = []): Verdict {
13  if (allowlist.some((a) => command.startsWith(a))) return { action: 'allow' }
14  for (const d of DESTRUCTIVE) {
15    if (d.re.test(command)) return { action: 'block', reason: d.why }
16  }
17  return { action: 'allow' }
18}

接线方式（三选一，按版本能力选择）：

  1. pre-execute 监听器调用 judge()，返回拒绝/询问（推荐，框架统一走审批 UI）；
  2. 包装 bash 工具的 execute，在调用真实实现前判定（Provider 层拦截）；
  3. 注册 command_check 工具让模型主动预检（最保守，零集成风险）。

模式二示例（Provider 层包装，只依赖已确认的 API）：

 1// 思路示意（伪代码）：ShellService 为示意基类，实际应替换为你要包住的那个 Provider
 2class GuardedShell extends ShellService {
 3  async exec(request: ShellRequest) {
 4    const verdict = judge(request.command, this.allowlist)
 5    if (verdict.action === 'block') {
 6      return { exitCode: -1, stdout: '', stderr: `blocked: ${verdict.reason}` }
 7    }
 8    return super.exec(request)
 9  }
10}

四、后台任务：长工作的正确生命周期

会跑很久的工具（全量重建索引、长视频转写）不该阻塞一次工具调用。DSH 里的真实分层是这样的：

角色包说明
抽象注册表@deepseek-ai/dsh-jobs提供 ctx.jobs：list / get / read / readAt / kill / wait / remove、events.subscribe
进程内实现@deepseek-ai/dsh-jobs-local任务真的在这个进程里跑
提供方控制器 + 三个工具@deepseek-ai/dsh-tool-jobs注册 job_output / job_list / job_kill，并附加 ctx.jobs.start() 得以启用所依赖的控制器

关键边界（原文）：组合里没挂 tool-jobs 的 agent 无法启动后台工作——控制器正是提供方 ctx.jobs.start() 的开关。所以"我有 ctx.jobs 却 start 不了"不是 bug，是缺控制器。

start(spec) 的完整形状（逐字核对自 npm 包 @deepseek-ai/dsh-jobs@0.2.1-rc.2 的 lib/types/types.d.ts；发行树把 .d.ts 剥掉了，所以只能从 npm 包或仓库源码看）：

 1ctx.jobs.start({
 2  kind: 'index-dir',                  // id 前缀：<kind>-<16 位 uuid>
 3  label: 'index ./docs',              // 模型可见的一行标签（命令、委派描述）
 4  owner,                              // 可选 SessionId；省略 = 无主任务，任何调用方可见
 5  toolCall: { callId, rootCallId },   // 可选；写进持久生命周期记录
 6  outputLimitBytes: 64 * 1024,        // 可选；单次模型侧读取/通知的字节上限
 7  output: [source],                   // 可选；注册表按自己节奏泵送的拉取源
 8  run(job) {                          // 预检通过后同步调用一次
 9    return {
10      cancel: (reason) => {},         // 必须同步、幂等，最终让 done 结算
11      done: Promise<JobOutcome>,      // 不得 reject（reject 会被转成 failed）
12    }
13  },
14})

job 是 JobHandle：{ id, append(text, options), updateProgress(line) }。output 里的每个源是 { channel?, read(fromByte) → { delta, nextOffset, lossy } }——只读、可重放，由注册表推进。

预检会先拒绝四类错误，且不会留下 job id：没有控制器（background jobs unavailable: no job controller serves this agent (load @deepseek-ai/dsh-tool-jobs in its composition)）、kind/label 为空串、outputLimitBytes 非正整数、超过每个所有者的并发上限（maxConcurrentJobsPerOwner）。

4.1 取消信号的语义（高频出错点）

任务发布后：
  exec.signal  →  只代表「不再等待这次调用」，不终止已发布的工作
  任务自有信号  →  真正终止任务（经任务终止工具触发）

官方警告原样照抄：绝不能通过解析「started background job bash-1」这种文本去取得 id。要拿 id，拿结构化字段 jobId。

4.2 设计稿：给 kb-lite 加一个「目录全量入库」后台任务

kb-lite 目前只有单文档入库。假设要新增「把整个目录递归入库」的能力，用后台任务模式实现（签名以当前版本 ctx.jobs 参考为准）：

 1// 设计稿：签名以当前版本 ctx.jobs 参考为准
 2output: {
 3  schema: {
 4    type: 'object',
 5    properties: {
 6      kind: { type: 'string' },     // 'background'
 7      jobId: { type: 'string' },
 8    },
 9  },
10  render: (_args, value) => [
11    { type: 'text', text: `已启动后台重建任务 ${value.jobId}，可用任务工具查看进度` },
12  ],
13},
14async execute(args, exec) {
15  if (!config.backgroundRebuild) throw new Error('后台重建未开启（backgroundRebuild=false）')
16  const job = await ctx.jobs.start({
17    name: 'kb-rebuild',
18    async run(signal) {
19      const files = await walk(args.dir)
20      for (const f of files) {
21        if (signal.aborted) return { cancelled: true }
22        await rebuildOne(f)
23      }
24      return { rebuilt: files.length }
25    },
26  })
27  return { kind: 'background', jobId: job.id }
28}

要点：是否允许后台由配置决定（不能写死）；run 接收任务自有 signal；返回句柄而不是文案；进度查询走任务输出工具。

4.3 没有 jobs 时的降级方案

如果组合里没有 ctx.jobs（或没挂 tool-jobs 控制器），用「分段 + 游标」模拟：kb_rebuild(dir, cursor?) 每次处理 N 个文件，返回 nextCursor，模型多轮调用推进。零新 API，且天然可取消（不调下一轮就停）。这也是给不装 jobs 的用户留的兼容路径。

五、审计与合规注意事项

  1. 日志脱敏：审计日志本身可能含密钥，记录侧脱敏（见第二节）；
  2. 最小采集：工具自己如实声明采集边界，别把整个文件系统状态倒进日志；
  3. 可回放性：卡片与展示数据用 presentationMeta 派生，不要存易变明文；
  4. 审批门：高危动作（写保护目录、外发数据）转人工，fail-safe 默认拒绝（对标 PerryLink/dsh-defend 的 allow/ask/block 三态）；
  5. 密钥来源：从环境变量或凭据库读，绝不写进 patch 文件提交 git。

七、练习

  1. 给 audit-lite 加 session/event 监听（签名 (session, event)），记录用户消息（event.type === 'user/message'）中的「记住：」捕获次数，输出日签到审计日志；
  2. 扩展 judge()：支持 allowlist 配置项，并为每条规则补单测（表驱动测试）；
  3. 把 kb-lite 的 kb_add 目录批量入库改造成 4.3 节的「分段 + 游标」模式，并处理 maxDocChars 边界；
  4. （进阶）把 judge() 以 pre-execute 接线，再写一条 ctx.tools.guard() 的红线规则，验证"guard 拒绝不可被放宽"。

小结

  • 策略与工具分离：判定器是纯函数，接线按流水线位置选：pre-execute（可否决/可询问）→ guard（单调拒绝）→ execute（包装）→ post-execute（可替换）→ result（只读审计）；
  • 两个稳定落点：tools/result 审计 + 工具化扫描，记录侧脱敏；
  • 后台任务分层：dsh-jobs（抽象 ctx.jobs）+ dsh-jobs-local（实现）+ dsh-tool-jobs（控制器与三工具）；没有控制器就 start 不了；
  • 后台任务三原则：配置开关、任务自有 signal、结构化 jobId 句柄；
  • 取消语义：exec.signal 止等待，任务信号止工作；失败/取消看结构化结果码，别解析文案；
  • 安全默认值：fail-safe 拒绝、最小采集、密钥不进 patch；
  • 下一篇收官：打包发布、测试策略与最佳实践清单。
